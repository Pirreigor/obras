CONTEXTO DEL PROYECTO "OBRAS"
=============================
Actualizado: 2026-08-17

QUE ES
------
Sistema de seguimiento de proyectos de construccion, multi-empresa (varias
constructoras pueden usar la misma app, con sus datos completamente
aislados entre si). Nace como un sistema TOTALMENTE APARTE del sistema de
joyeria (Don Joyero, carpeta ../joyeria), para que el equipo de la joyeria
no tenga ninguna visibilidad ni acceso al de la constructora, ni viceversa.

Primera empresa cargada: "JJAM".

ESTADO ACTUAL: YA ESTA DESPLEGADO Y EN VIVO
---------------------------------------------
https://obras.donjoyero.com esta funcionando en produccion (frontend +
backend + base de datos real), probado end-to-end (login real incluido).
Faltan las pantallas de negocio (Obras/Sub-obras/cronograma/pedidos); lo
que existe hoy es: login, y las pantallas de alta de empresas (superadmin)
y de equipo/invitaciones (administrador/supervisor).

DECISIONES TOMADAS (y por que)
-------------------------------
1. Repo propio, sin relacion con joyeria.
   - joyeria/ es un solo repo git con admin/backend/frontend adentro.
   - obras/ es OTRO repo git independiente: https://github.com/Pirreigor/obras

2. Dominio: subdominio del dominio que ya existe para la joyeria.
   - obras.donjoyero.com. Registro DNS tipo A -> 104.131.19.189 ya creado
     y propagado.

3. Base de datos: DB nueva dentro del MISMO cluster de Postgres de DO
   (cluster "joyeria-db", ahorra costo, DO lo permite gratis).
   - Base: obras_db. Usuario propio: obras_user (NO doadmin, NO el user de
     joyeria).
   - IMPORTANTE - hallazgo de seguridad (2026-08-17, sin resolver todavia):
     por defecto en DO, cualquier usuario nuevo del cluster puede
     CONECTARSE a las demas bases del cluster (incluida defaultdb, la de
     joyeria), aunque NO puede leer datos (confirmado: "permission denied"
     al hacer SELECT sobre una tabla real de joyeria). Para cerrar esto del
     todo falta correr, con doadmin:
       REVOKE CONNECT ON DATABASE defaultdb FROM obras_user;
     Se decidio dejarlo pendiente (no bloqueante) por ahora.
   - Para que obras_user pudiera migrar/crear tablas en obras_db hubo que
     correr (con doadmin, una sola vez):
       ALTER SCHEMA public OWNER TO obras_user;
       ALTER DATABASE obras_db OWNER TO obras_user;
     (Un usuario nuevo en DO no es dueno de su propia base por default.)
   - OJO: en algun momento de esta configuracion la contrasena de doadmin
     quedo pegada sin querer en un chat. Convendria rotarla en DO
     (Databases -> joyeria-db -> Users & Databases -> doadmin).

4. Despliegue: mismo Droplet que joyeria, carpeta y proceso separados.
   - Droplet: ubuntu-s-1vcpu-1gb-nyc3, IP 104.131.19.189, NYC3, Ubuntu
     24.04, 1GB RAM / 25GB disco. Node v22, PM2, Nginx.
   - joyeria: /var/www/joyeria, proceso PM2 "joyeria-api" en puerto 4000.
   - obras: /var/www/obras (repo clonado ahi), proceso PM2 "obras-api" en
     puerto 4100, bloque Nginx propio (/etc/nginx/sites-available/obras)
     que sirve el frontend como estatico (frontend/dist) y proxea /api/ al
     puerto 4100. Certificado TLS propio via certbot para
     obras.donjoyero.com (NO comparte ni modifica el certificado de
     joyeria, que sigue cubriendo donjoyero.com/www/erp/api).
   - Memoria: con los dos procesos Node corriendo, quedan ~500MB
     disponibles de 961MB totales. Ajustado pero funciona; vigilar con
     `free -h` / `pm2 list` si se agregan mas procesos.
   - Acceso SSH: se genero una key dedicada (obras_deploy_ed25519) agregada
     a ~/.ssh/authorized_keys de root para el despliegue asistido. Convendria
     quitarla de authorized_keys cuando ya no se necesite acceso recurrente.

5. Stack tecnologico (igual al de joyeria, por consistencia):
   - Backend: Node.js + Express 5 + Prisma ORM + PostgreSQL. JS plano
     (sin TypeScript). Auth con JWT + bcrypt.
   - Frontend: React 18 + Vite. JS plano.

MODELO DE DATOS Y ROLES (multi-empresa)
------------------------------------------
Jerarquia: Empresa -> Zona -> Localidad -> Obra -> SubObra

Roles (enum Rol):
  SUPERADMINISTRADOR - sin empresaId, existe fuera de toda empresa. Unico
    que crea registros de Empresa (y de paso su primer ADMINISTRADOR).
  ADMINISTRADOR      - por empresa. Gestiona Obras/Sub-obras, invita usuarios.
  SUPERVISOR         - por empresa, ve TODO (todas las zonas/localidades/
    obras) en modo lectura global; tambien puede invitar usuarios.
  RESIDENTE          - uno por Obra. Ve/gestiona su Obra y las Sub-obras
    de esa obra, puede reportar avances.
  CALIDAD_PRODUCCION - por Sub-obra. Reporta avances/actividades de su
    sub-obra, lee el progreso general de la Obra padre.

Entidades principales (ver schema.prisma para campos exactos):
  Empresa, Zona, Localidad, Obra, SubObra
  ActividadCatalogo / ActividadProgramada / RegistroDiario (cronograma;
    RegistroDiario es 1 por dia trabajado, no un rango de fechas)
  Avance (reporte con fotos, ligado a SubObra y opcionalmente a una
    ActividadProgramada)
  MaterialCatalogo / PedidoMaterial / PedidoMaterialItem /
    PedidoItemSubObra (un pedido puede repartirse entre varias sub-obras;
    ver diagrama de referencia mas abajo)
  Invitacion (alta de usuarios por link, ver ALTA DE USUARIOS)

Diagrama de referencia (jerarquia, cronograma, pedidos compartidos):
  https://claude.ai/code/artifact/644dad6c-16f7-4d8d-a782-de24586f1fb4
  (nota: este diagrama es de ANTES de agregar Empresa como raiz; el resto
  sigue vigente)

ALTA DE USUARIOS (sin registro publico)
-------------------------------------------
No existe /api/auth/register. El flujo es:
  1. SUPERADMINISTRADOR crea la Empresa + su primer ADMINISTRADOR
     (POST /api/empresas).
  2. Ese ADMINISTRADOR (o un SUPERVISOR) invita gente por email:
     POST /api/auth/invitaciones {email, rol} -> genera un token.
  3. El invitado entra a /aceptar-invitacion?token=... y define nombre +
     contrasena (POST /api/auth/aceptar-invitacion) -> cuenta activa.
  PENDIENTE: el correo de invitacion NO se envia solo todavia (no se
  eligio proveedor de email). Por ahora el link se muestra en pantalla
  para copiar y compartir a mano.

NOTAS DE SEGURIDAD
-------------------
- backend/.env.example es solo una plantilla, sin credenciales reales.
- backend/.env real vive SOLO en el servidor (/var/www/obras/backend/.env,
  permisos 600), nunca en git.
- obras_user es un usuario de Postgres propio y distinto de doadmin y del
  usuario de joyeria, con permisos acotados a obras_db (ver salvedad del
  REVOKE CONNECT pendiente, arriba).
- El JWT_SECRET de obras es distinto al de joyeria (generado con
  openssl rand -hex 48).
- SUPERVISOR tiene alcance global solo DENTRO de su propia empresa (no
  cross-empresa; eso es exclusivo de SUPERADMINISTRADOR). El rol por
  defecto de cualquier alta que no especifique rol es CALIDAD_PRODUCCION
  (el de menor alcance) a proposito, para evitar escalacion de privilegios.
